## 3. Deterministic loop

1. Load the latest config and check any pending transaction before starting another operation.
2. Read balances and usable prices for the configured assets. Use correct decimals and integer base units; weights total 10,000 basis points. Missing/stale prices or an unavailable route produce no trade.
3. Calculate allocation drift. If it exceeds the configured threshold, compute one corrective swap through the quote asset. Ledger mode can do this from its saved public address while disconnected; retain a needs-rebalance status and require an explicit request on its running monitor before signing. For partial target edits, proportionally redistribute the other weights with deterministic rounding.
4. Apply the persisted cycle interval before preparing new execution. By default a new cycle can start once an hour; its fixed ten-minute active window allows sequential approval/swap legs after each receipt resolves. Window expiry stops new dispatches, while pending receipts still reconcile. Restarts and target edits do not extend the window or reset the next eligible start.
5. Build the transaction for Robinhood chain ID 4663 using its token addresses, wallet recipient and Uniswap router. Check available balance and enough native currency for estimated gas. Keep the route's slippage/minimum-output and expiry settings, bounded by the active window. Skip zero-sized trades.
6. Before each dispatch, save a minimal pending marker with the selected chain/account and nonce or available provider request identifier. Persist cycle timing before its first dispatch. Execute automatically with local-key/Privy, or consume a user-authorized Ledger rebalance request and obtain physical confirmation for each transaction. Make required token approvals for the swap amount through the same signer; do not build an allowance-management product.
7. Update the pending record with the returned transaction/provider identifier and wait for its receipt. Refresh balances before calculating another trade, including a buy dependent on earlier sale proceeds.

Keep one pending operation at a time per wallet. Each wallet owns its allocation, state, cadence and independent deterministic runner; chat attachment only selects control/display scope. The original legacy data stays in place; additional wallets use isolated directories and chart ports. See [wallet portfolios](docs/PORTFOLIOS.md). Its pre-dispatch marker and subsequent transaction/provider identifier allow restart reconciliation. If a send may have succeeded but its identifier was not recorded, stop new execution with unresolved status rather than sending again. On Ledger rejection, keep monitoring and end that signing request. Only a new user-authorized rebalance request can permit another attempt; reconnecting and polling cannot reopen it. An explicit request quietly records the drift condition so rejecting it does not create a fresh chat alert. The persisted cadence limits cycle frequency; it is not a gas budget or a one-transaction-per-hour guarantee. The [recovery stage](docs/RECOVERY.md) automatically handles stale raw-key and Privy sends after a fixed 30-second grace, with one zero-value cancellation at the same nonce. It retains both identities until a verified winning receipt; it never blindly retries an uncertain cancellation. A confirmed cancellation or original revert can continue the current active window. Canonical successful swaps are marked before pending is cleared: cycles with a successful swap retain hourly timing, while new cycles with no successful swap may retry after their original ten-minute window. Legacy records remain conservative. It does not invoke an LLM, stop/start itself or introduce a generic escalation framework. Full raw-key or Privy launch can enter this automatic-recovery graph through unresolved/reverted state after successful preflight, preserving pending/cycle records; no separate user recovery or stop/start sequence is required. Setup-only does not enter this path. Full Ledger launch enables public receipt/drift monitoring without cancellation or signing intent. Ledger unknown sends remain receipt barriers, and confirmed reverts need the existing explicit receipt-recovery workflow; it never signs automatic cancellations. The explicit recovery command remains optional for automatic signers. See [the startup and gas-label correction](docs/prompts/029-automatic-launch-recovery-and-gas-label.md).

For Ledger, a connection event, startup with the device already attached, or new excessive drift while connected triggers a fresh check. First reconcile pending sends, then reload config/balances and recalculate drift. If action is still needed and cadence permits, retain one actionable alert through the agent. Retain undelivered alerts if the agent is unavailable; notification delivery uses the existing agent integration, with no LLM calls in monitoring. Alerts are separate from signing requests. An explicitly authorized `ledger rebalance --request-id <UUID>` must be claimed within two minutes and expires at the earlier of ten minutes after creation or its bound cycle deadline. Only the claiming runner retains in-memory authority for fresh, sequential, physically confirmed approval/swap transactions. A fresh on-target observation ends the request and clears the drift condition. Read [the implemented Ledger workflow](docs/LEDGER_EXECUTION.md).

Hardware detection is distinct from readiness to sign: check the Ethereum app/device state and selected account before requesting the signature. Connecting never authorizes a swap. Do not retain an old unsigned transaction as ready to execute after reconnect; refresh it. A disconnection after submission still requires receipt reconciliation, including any approval already sent.

If configuration, runner identity or USB connection changes while a Ledger request is pending, end its authority. A new explicit request must refresh the current portfolio and quotes. Device approval applies to the exact transaction being signed. Stop cancels an outstanding device prompt and prevents new dispatch; it does not undo a broadcast transaction. Reconcile earlier submitted hashes before further work. A consumed request cannot resume after restart or cross into a second cycle.

These are the mechanics needed to produce the intended swap, not a separate security or spending-policy system. Keep keys/API secrets in ignored local configuration or the selected provider's credential mechanism, outside chat, source control and logs. Use the selected signer/account explicitly; no silent backend fallback.
